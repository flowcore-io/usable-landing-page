Connect a tool-capable AI agent to Usable with auth.md

August 21, 2026 Updated August 22, 2026 Usable Team 7 min read

auth.md documents Usable's machine-readable service_auth protocol. It works only in runtimes that can make arbitrary HTTPS requests, poll the claim, protect bearer secrets, and configure an MCP or API connection. Reading auth.md alone does not give an ordinary chat those capabilities.

Check your client before you start

A compatible runtime needs every capability below before it asks for your email address or creates a pending registration:

  • Make arbitrary HTTPS GET and POST requests to discovered Usable endpoints.
  • Poll the claim endpoint at the returned interval and handle protocol responses.
  • Keep the issued bearer credential in an approved secret store outside chat and logs.
  • Configure an MCP or API client, prove an authenticated read, and revoke the credential.
  • Use an installed, allowlisted Usable connector or explicit operator authorization restricted to exact Usable endpoints.
  • Provide a trusted, non-transcript human handoff for the claim link and six-digit code.

Fetching auth.md does not authorize a client to bypass its security policy. If the chat has no trusted Usable connector or general HTTP action, no claim can be created and no approval URL exists. A text-only chat is unsupported even if it can POST.

What a compatible runtime does

The protocol is a guided handoff only after the runtime passes its capability checks. No successful POST means no approval URL exists. Never construct, guess, or “fix” an approval URL. Treat the exact returned claim.verification_uri as short-lived sensitive handoff material: open it only for the approving user through the trusted handoff, and never persist, rewrite, forward, or print it into the transcript.

  1. 1

    Preflight capabilities

    Confirm outbound HTTPS, polling, approved secret storage, and an MCP or API configuration surface before collecting an email address.

  2. 2

    Discover and validate

    Read auth.md and the exact OAuth discovery URL, require agent_auth, and restrict requests to declared endpoints whose origin is exactly https://usable.dev.

  3. 3

    Create the claim

    Ask for the email only when ready to submit. Store claim_token; open the exact returned verification URI through the trusted handoff and enter user_code only on https://usable.dev.

  4. 4

    Approve, poll, and configure

    You sign in and approve. The runtime respects the polling interval, handles authorization_pending and slow_down, stores the issued bearer credential, configures the client, and proves an authenticated read.

Fail closed when a capability is missing

If the runtime lacks outbound POST, polling, approved secret storage, a trusted human handoff, or MCP/API configuration, it must stop before starting a claim and explain the missing capability. It must also stop when agent_auth is absent or any endpoint origin is not exactly https://usable.dev.

Discard expired or rejected claims and restart from discovery. Wait on authorization_pending; increase the interval on slow_down. Any guessed approval URI fails the flow. Revoke any credential that is exposed or no longer needed.

Never place claim_token, user_code, the verification URI, or the bearer credential in chat or logs.

What remains human-controlled

The agent does not create your Usable account or make payments in this first phase. You create or sign in to the account, accept the terms, choose a plan when needed, and explicitly approve access. This keeps identity, consent, and billing decisions with you.

A compatible runtime can

  • Discover the supported authentication flow
  • Create and poll a pending registration
  • Store and configure the issued credential after approval
  • Revoke the credential when it is no longer needed

You control

  • Creating or signing in to the Usable account
  • Accepting terms and reviewing requested access
  • Confirming the browser origin is exactly https://usable.dev
  • Approving the agent
  • Selecting and paying for a plan

Designed to avoid token copy-paste

The browser handoff uses short-lived claim material. After approval, the polling client—not the browser—receives the bearer credential. Store it in an approved secret store outside the transcript and logs, verify the configured connection, and revoke it when no longer needed.

Already have a Usable account? The same flow signs you in and moves directly to review. New to Usable? Account creation, terms, and approval happen in one browser journey.
