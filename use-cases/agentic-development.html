The engineering problem

A fast agent without organisational context makes mistakes faster

A coding agent can inspect a repository, trace call paths, edit files, and run commands. That local view is necessary, but it is incomplete. The reason a team rejected an earlier approach, the architecture rule shared by several services, a customer commitment that shaped acceptance criteria, or an incident lesson that changed deployment practice may live outside the checkout.

When that context arrives only in review, the agent can produce code that is technically plausible and organisationally wrong. The better pattern is a controlled delivery loop: inspect the live system, retrieve the durable knowledge relevant to this task, surface conflicts before coding, preserve human decisions, verify the change, and write proven learning back for the next task.

Usable is the durable memory in this loop—not the source of every truth. The repository remains authoritative for current code; the task or PRD for accepted scope; Git and CI for review evidence; and deployment and observability systems for production state.

Give every source a clear job

Agentic development becomes safer when the agent knows where to look and which system can settle each question. Copying all context into one knowledge base creates drift. Linking the systems by purpose creates traceability.

SourceWhat it should establishWhat it should not claim
Task, issue, or PRDDesired outcome, scope, acceptance criteria, priority, and unresolved product decisions.That a change is implemented, merged, or deployed.
Repository and worktreeCurrent code, configuration, dependencies, tests, local instructions, and existing conventions.The complete history behind every choice.
Usable workspaceDurable standards, domain maps, architecture decisions, approved plans, runbooks, prior solutions, and verified learnings across tasks and repositories.Live branch state, passing CI, or current production health.
Git, pull request, and CIThe intentional diff, review discussion, approvals, and checks executed for a specific revision.That the revision is running successfully in production.
Deployment and observability systemsRelease state, configuration, rollout health, incidents, and rollback evidence.The original product intent or undocumented policy.

Volatile facts—current code, package versions, open review threads, build results, and service health—should be fetched from their live source. Durable reasoning belongs in maintained fragments. A link between them is more useful than a stale copy.

Store the context that changes engineering decisions

Usable organises knowledge as fragments inside workspace boundaries. Teams can use precise types such as Knowledge, Plan, PRD, Recipe, Solution, Template, Research, or Skill, then add summaries, tags, status, ownership, and links. Collections can assemble a project packet without duplicating its contents. Humans work through the dashboard; scripts can use REST; AI clients can search, fetch, create, and update through MCP when authorised.

The most valuable engineering fragments are not generic explanations. They change what the implementer should do:

  • Standards and architecture decisions with scope, constraints, alternatives, and consequences.
  • Domain maps that route an agent to mandatory doctrine, conditional guidance, negative constraints, and known failure modes.
  • PRDs and accepted plans that preserve outcomes, vertical slices, assumptions, verification expectations, and human decisions.
  • Runbooks and deployment guidance owned by the people who operate the system.
  • Proven solutions and implementation learnings tied to the change and verification evidence that established them.
  • Customer-safe requirements and incident lessons that alter product, security, reliability, or support behaviour.

Keep executable code and current configuration in the repository. Keep secrets in a secret manager. Avoid raw logs, customer data, private credentials, complete chat transcripts, and temporary debugging notes. Durable memory should be specific, sourceable, sanitised, and safe to retrieve later.

Ground the agent before it writes the plan

The order matters. Searching organisational memory without inspecting the target repository produces generic advice. Inspecting only the repository repeats decisions the organisation has already made. A useful preflight combines both.

  1. Read the task as a contract. Identify the intended outcome, acceptance criteria, exclusions, dependencies, risk, and decisions that still require a person.
  2. Inspect the local checkout. Read repository instructions, the working tree, project structure, package scripts, representative routes, components, event paths, schemas, tests, and deployment files. Preserve unrelated user changes.
  3. Search the correct workspace. Ask in natural language for the standards, domain maps, PRDs, decisions, earlier plans, and prior solutions relevant to the repository and feature. Repository and domain tags can narrow the search, but they should not hide cross-project guidance.
  4. Fetch the full source. Search results and chunk previews are discovery aids. Before a fragment constrains a plan, retrieve its complete content and check its status, date, scope, and provenance.
  5. Build a constraint record. Summarise which sources shape the task, what each requires, where repository reality differs, and which questions remain open. If nothing relevant exists, say so and continue from local evidence rather than inventing an organisational rule.

Why domain maps matter

A domain map is a compact routing contract for context re-inflation. Instead of relying on a prompt to remember every standard identifier, it tells the agent which doctrine is mandatory, which references apply only under certain conditions, which constraints cannot be compressed away, and which failure modes deserve an explicit check. It reduces accidental omission while allowing the detailed standards to evolve independently.

A map is still not implementation truth. The agent must fetch the referenced sources and compare them with the repository. If an active standard and current code disagree, that is a decision point—not permission to choose whichever is easier.

Turn grounded context into a reviewable plan

A plan is the first quality gate. It should be small enough to review and explicit enough that the team can see a wrong assumption before it becomes a large diff. For substantial work, prefer thin vertical slices that each deliver a narrow behaviour through its required layers and can be verified independently.

Plan fieldQuestion it answers
Outcome and exclusionsWhat user or operational result will change, and what is intentionally not included?
Grounding sourcesWhich task, repository evidence, standards, decisions, and prior solutions shaped the plan?
Implementation slicesWhat is the smallest ordered path that produces demonstrable value?
Constraints and conflictsWhich rules are mandatory, and where do sources disagree?
VerificationWhich static checks, tests, runtime checks, and acceptance evidence will prove each slice?
Delivery boundaryDoes the task authorise only code changes, or also commit, push, merge, release, or deployment?
Rollout and recoveryHow will the change be observed, limited, rolled back, or repaired?
Human gatesWhich product, architecture, security, data, cost, or irreversible decisions need explicit approval?

Save a meaningful plan in Usable when it has value beyond the current chat: include the project or repository, source task and decisions, slices, assumptions, verification expectations, and later deviations. Do not duplicate documents already owned elsewhere; link to them and record the durable engineering interpretation.

Keep judgement and authority with people

An agent can investigate options and recommend a path. It should stop when proceeding would invent product behaviour, cross a security boundary, expose private data, require an irreversible operation, or materially expand scope. The human gate should state the decision needed, available evidence, recommended option, alternatives, and consequence of delay.

Conflicts should fail closed. If a current standard forbids a pattern present in the repository, if two active requirements disagree, or if a production change lacks a clear owner, the agent should identify the exact conflict and ask the responsible person to decide. Once resolved, update the authoritative source so the next task does not reopen the same ambiguity.

Never hide an architecture conflict behind a fallback. A direct-write shortcut, silent mock, disabled check, or unapproved compatibility path can make a test pass while defeating the system the standard was designed to protect.

Implement in small increments and prove what changed

Once the plan is approved, the agent works against the actual repository: follow existing module boundaries and naming, add dependencies through the repository's package manager, preserve the lockfile, and keep the diff intentional. Tests should exercise the public behaviour appropriate to the change, not merely private implementation details. For a vertical slice, one end-to-end tracer test can establish the path before broader edge cases are added incrementally.

Verification is layered. The exact commands come from the repository, but the evidence often includes:

  • Static checks: formatting, linting, type checking, schema or architecture guardrails.
  • Focused tests: unit and regression checks around the changed behaviour.
  • Integration tests: real boundaries between modules, persistence, events, authentication, or external adapters where feasible.
  • User-path checks: browser or end-to-end flows covering success, loading, empty, failure, and permission states relevant to the feature.
  • Build and runtime checks: production build, local service health, migrations, or a safe smoke test.
  • Security and privacy checks: authorisation, tenant boundaries, input validation, secret handling, and sanitised telemetry.

Record commands and outcomes accurately. “Tests pass” means the stated tests ran successfully against the stated revision and environment. A skipped test, unavailable credential, unhealthy local dependency, or known repo-wide failure belongs in the result as a limitation—not behind a confident summary.

Use the pull request as an evidence boundary

The commit and pull request should explain intent, source constraints, the significant choices made, verification performed, known risks, and any follow-up. Conventional commit structure and PR templates can make this consistent where the repository requires them. A clean diff helps both human and automated review distinguish the feature from incidental churn.

CI is authoritative for the checks it actually runs. Automated validators can compare a diff with selected standards and security rules, but they are an additional gate, not a substitute for tests or human review. Validators must cite code evidence, use current standards, and make exceptions explicit and reviewable. Reviewers still own architecture, product behaviour, security judgement, and whether the evidence is sufficient.

Keep delivery states distinct: changed locally, committed, pushed, reviewed, CI-green, merged, released, deployed, and verified in production are not synonyms. An agent should report the last state it can prove.

Do not let coding authority silently become production authority

A request to implement a change normally authorises repository work, not an automatic merge or production deployment. Release and deployment follow the repository's documented process and the organisation's deployment authority. GitOps configuration, release automation, environment promotion, and live telemetry remain the source of truth for those stages.

Where an authorised workflow reaches deployment, the plan should name the environment, credential scope, migration order, rollout signal, health check, rollback condition, and owner. Agents should use the narrowest credentials required and should never store source-control tokens, signing keys, cloud credentials, customer payloads, or secret values in Usable. A missing credential or ambiguous target is a hard stop, not a reason to invent a bypass.

Write back verified learning, not activity

After implementation and verification, update the approved plan with deviations and create or improve the relevant learning. The writeback should make the next task easier without forcing its agent to replay the entire conversation.

A useful implementation learning records

  • The repository, branch, task, pull request, or release context needed to locate the change.
  • The decision made and why it differed from obvious alternatives.
  • The modules and public behaviour changed.
  • The exact checks run, their outcomes, and the environment that produced them.
  • Failures encountered, the proven fix, and conditions under which it applies.
  • Residual risks, skipped verification, rollout dependencies, and sensible follow-up.

Prefer updating an existing relevant fragment over creating a near-duplicate. Promote a lesson into a standard only after review establishes that it should govern future work. Temporary hypotheses, unreviewed recommendations, and failed experiments can be useful research, but they should be labelled as such.

An anonymous example: the shortcut that should not ship

A team asks an agent to add a mutation to an established service. Local inspection reveals a convenient direct persistence call in an older module. Organisational search finds a current domain map and architecture decision requiring mutations in this area to enter through an event path, with projections responsible for persistence. A prior verified learning warns that a fallback to direct persistence hid delivery failures during testing.

The agent fetches all three full sources, identifies the older code as a conflict rather than a pattern to copy, and presents a vertical-slice plan: validate the public request, emit the bounded event, project it idempotently, expose processing status, add a tracer test through the public interface, then cover replay and failure behaviour. A human confirms scope and the migration boundary.

Implementation passes focused checks locally. The pull request records the cited constraints and verification. CI provides the canonical integration evidence; deployment remains pending because the original task did not authorise it. The agent updates the saved plan with the deviation and writes back the verified replay lesson. The next service can retrieve the rule and the evidence without learning a customer name, private repository path, credential, or operational secret.

Connect engineering memory to the rest of the organisation

Agentic development improves when neighbouring workflows contribute concise, governed inputs—and when engineering returns safe evidence instead of private implementation detail.

Neighbouring workflowWhat engineering can retrieveWhat engineering can return

Onboarding & role changeRole-specific standards, project decisions, environment setup, and escalation paths.Verified setup corrections and recurring gaps in the onboarding path.

Use customer-safe derivatives for cross-team reuse. Remove names, personal data, private repository details, internal hostnames, and security-sensitive operating information. Access control is still essential: a useful link does not mean every workspace should be visible to every agent.

Separate current Usable capabilities from configured workflow

Usable currently provides the core pieces required for this memory layer: workspaces, typed memory fragments, collections, files and attachments, the human dashboard, REST APIs, and MCP tools for AI clients. Workspace membership and token permissions control access; personal access tokens should be scoped to the smallest permissions and workspaces required.

The complete delivery loop described here is an operating model. Task-system connections, domain-map conventions, PR validators, CI gates, deployment automation, writeback templates, and review cadences depend on how each organisation configures its tools and responsibilities. Storing a standard does not automatically enforce it. Connecting an agent does not give it every integration. A team must deliberately wire the retrieval, authority, permissions, and review boundaries it wants.

Govern the memory like engineering infrastructure

  • Scope access. Use read-only credentials for research where possible; grant create or update rights only to workflows that need writeback.
  • Make authority visible. Include owner, status, scope, source, review date, and supersession links for material standards and decisions.
  • Prefer full UUIDs and stable keys. Precise identifiers prevent the agent from retrieving or linking the wrong source.
  • Resolve contradictions. Archive or supersede obsolete guidance and record the decision that replaced it.
  • Review generated writeback. Agents may draft a learning, but evidence and classification determine whether it becomes organisational authority.
  • Keep private data private. Sanitise examples, use workspace boundaries, and exclude secrets and unnecessary customer information.

Adopt the loop one repeated problem at a time

  1. Choose one repository and one recurring review correction. A narrow, costly pattern is easier to validate than an organisation-wide rollout.
  2. Inventory existing authority. Identify the task source, repo instructions, current standards, relevant domain map, deployment process, and owners.
  3. Capture the minimum useful memory. Improve missing or ambiguous sources; do not import every document indiscriminately.
  4. Run real tasks. Require local inspection, scoped search, full-source fetch, a cited plan, explicit decisions, verification, and writeback.
  5. Review retrieval and outcomes. Correct false matches, stale sources, missing constraints, and writebacks that overstate evidence.
  6. Expand only after reuse works. Add another task class or repository when a later agent can reliably find and apply what the first work proved.

The goal is not the largest workspace. It is a maintained memory layer that improves real decisions while preserving clear authority.

Expect limits. Retrieval can miss a relevant fragment. A well-written fragment can still be outdated. Tests can be incomplete. A green pull request can still fail after deployment. Usable makes organisational context durable and available to agents; it does not replace repository inspection, engineering judgement, code review, CI, deployment control, or production observation.
