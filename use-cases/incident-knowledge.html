The operational problem

Recovery is urgent; learning must still be governed

During an incident, responders assemble a fast-changing body of evidence: reported impact, failing requests, service health, traces, logs, platform events, dependency state, metrics, changes, hypotheses, attempted mitigations, and verification results. If that material remains only in a chat channel, dashboard, ticket, or one operator’s memory, the next responder must reconstruct it under pressure.

The answer is not to copy every raw signal into a knowledge base. Telemetry, alerting, ticketing, status, change, and communication systems remain authoritative for their live data and execution history. Usable is the governed memory layer: it preserves the reviewed investigation, verified solution, decision context, prevention work, and reusable operational guidance that should outlive the event.

Our operating model treats investigation and documentation as one lifecycle with two different modes. First, an evidence-led working log helps restore service safely. After recovery is confirmed, that raw record is transformed into linked, reviewable knowledge for future operators, developers, service teams, customer-facing colleagues, and approved AI clients.

This boundary prevents two dangerous shortcuts: treating memory as live telemetry, and treating a dashboard as durable explanation. A fragment can explain how to interpret an alert, but it cannot prove the system is currently healthy. A monitor can show recovery, but it does not explain why the fix was safe or how the organisation should prevent recurrence.

Start by defining the investigation, operator, and proof of recovery

Before querying infrastructure or changing anything, initialise the investigation. Our incident protocol begins with explicit parameters because an unbounded investigation can mix incidents, destroy a previous record, or “verify” a fix by a method nobody agreed to.

  1. Confirm identity and incident parameters. Record date and time, responsible operator or incident lead, issue type, affected capability if known, reported symptoms, start time, recent changes, and user or customer impact.
  2. Protect the previous working log. Check whether the temporary investigation record already contains another case. Back it up, archive it, or clear it only with operator approval. Never silently overwrite operational history.
  3. Inventory available tools and access. Confirm which telemetry, cluster, cloud, deployment, ticket, and testing tools are available. Document gaps and agree whether to proceed with reduced evidence or obtain additional access.
  4. Agree the verification method. Decide upfront whether recovery will be proven by repeating the original failure path, automated tests, manual user verification, monitored stability, or a combination.
  5. Open the factual running log. Timestamp actions and observations, write objectively, distinguish operator report from measured evidence, and keep facts separate from interpretation.

The working log is not the polished outage report. It is the investigation’s chain of reasoning, including failed tests and changed hypotheses. Its job is to make the response inspectable while events are still moving.

Move from the symptom to the full dependency chain

Similar user-facing errors can come from very different failure modes. A previous solution is useful orientation, not proof that the same cause has returned. The investigation must narrow the current case from live evidence.

  1. Reproduce or positively identify the symptom. Capture the exact request or user journey, observed result, timestamp, duration, scope, and error. If reproduction would be unsafe, define an equivalent read-only signal.
  2. Assess service health. Check readiness, instance count, restarts, error rate, latency distribution, resource pressure, and whether the problem is isolated or widespread.
  3. Inspect traces. Follow failed or slow requests across components. Compare success and failure populations, duration patterns, missing spans, versions, and where the path diverges.
  4. Inspect logs. Start with broader patterns, then narrow to exact records around the relevant time. Record both the matching error and the absence of expected activity.
  5. Inspect platform and workload events. Look for restarts, health-probe failures, scaling, scheduling, resource exhaustion, deployment, or other lifecycle changes.
  6. Map the dependency and data flow. Describe the normal processing chain, ownership, backing services, external dependencies, expected timing, and the point where observed behaviour departs from normal.
  7. Check monitors, metrics, and infrastructure. Confirm alert state, query the relevant time series, inspect backing and cluster layers, and note where a healthy aggregate hides a failing path.
  8. Expand the time window. Compare current signals with earlier hours or days to distinguish sudden failure, gradual degradation, recurrence, and unrelated historical noise.

Every tool result has limits: retention windows, sampling, query mistakes, missing instrumentation, permissions, and false “no data” results. Where absence matters, use a positive control—prove the query can see known traffic or state before treating an empty result as an all-clear.

Keep an evidence ledger, including dead ends

Form hypotheses only after enough evidence exists to explain the symptom and the dependency chain. For each candidate cause, record what supports it, what contradicts it, what test would discriminate it, and the current confidence. Do not erase an early assumption when evidence changes the conclusion.

A root-cause statement should explain the evidence chain, user impact, failure mechanism, contributing conditions, and why existing controls did not catch or prevent it. If the evidence proves only a mitigation, say so. “Recovered after a change” is not automatically “root cause confirmed.”

Approval comes before remediation; verification comes after

Once the evidence supports a course of action, propose the remediation with its blast radius, prerequisites, rollback, owner, and expected observable effect. The operator or incident lead approves the change before it is executed. An AI assistant’s ability to call a tool is not authorisation to change production.

  1. State the proposed action. Connect it directly to the evidence-backed hypothesis and identify what would falsify the reasoning.
  2. Assess risk and rollback. Describe affected users and dependencies, data or availability risk, required access, and how the change can be reversed.
  3. Obtain explicit approval. Record who approved, what scope was approved, and any conditions. Re-approve if the action changes materially.
  4. Execute through the authoritative system. The deployment, infrastructure, or administration system records the actual change; the investigation log records why it was done and what happened.
  5. Repeat the original failure path. Use the verification method agreed at initialisation. Confirm the symptom is gone, not merely that a dashboard looks calmer.
  6. Check stability and side effects. Observe the agreed period, compare relevant metrics with baseline, inspect fresh errors, verify dependent paths, and record any remaining uncertainty.

A previous Solution fragment never grants permission to act blindly. Confirm that the current signature, architecture, version, scope, prerequisites, and rollback match. If they do not, use the prior solution as evidence for a new investigation—not as a shortcut around it.

Close the incident before converting it into durable memory

Closure records the final operational state: resolved, partially resolved, monitoring, or unresolved; the evidence-backed root cause or remaining hypothesis; the applied remediation; confidence; service health; user impact; timing; and outstanding risk. Separate what restored service from what prevents recurrence.

Group recommendations by urgency and assign an accountable owner and due point:

  • Immediate: actions already taken to restore or protect service.
  • Short term: monitor, runbook, configuration, test, or operational changes that prevent the same failure.
  • Medium term: resilience and observability improvements across dependencies.
  • Long term: architecture, ownership, capacity, or product changes that remove a systemic condition.

Only after the investigation is complete, remediation is verified, and the working log is complete should the team create reusable knowledge. If the incident remains ambiguous, publish that uncertainty rather than manufacturing a neat story.

Create two linked records for two future needs

Our operations workspace uses a custom Outage Investigation fragment type alongside the standard Solution type. The documented workflow converts the reviewed working log into two linked records rather than one oversized postmortem.

Link them both ways in content and metadata, then verify that search can find each from its symptoms, failure mode, affected area, and related record. The Solution must never omit the requirement to confirm the current case. The Investigation must never hide rejected hypotheses that explain why the chosen remediation was justified.

Before publication, remove secrets, personal data, customer payloads, private addresses, raw sensitive logs, and identifying infrastructure detail that is not necessary for the intended audience. Keep a source reference where authorised. A sanitised record should remain useful without pretending that redacted evidence was never consulted.

Push the lesson into monitors, runbooks, tests, and standards

An incident becomes organisational improvement only when it changes future detection or behaviour. The outage report should identify which signal could have detected the condition earlier, which monitor failed or misled, and which development or operational control allowed the failure.

  • Monitoring: define the signal, scope, aggregation, threshold, time window, severity, no-data behaviour, recipient, rationale, and evidence that the proposed monitor would have detected the incident without unacceptable noise.
  • Runbooks: add the safe first checks, escalation point, discriminating evidence, prerequisites, rollback, and verification—not only the command that happened to work.
  • Development: update architecture decisions, contracts, service templates, automated tests, deployment checks, and standards where the contributing condition can be prevented at build or review time.
  • Ownership: assign each action, keep its status in the appropriate task system, and link the completed evidence back to the investigation.
  • Exercises and onboarding: use a sanitised scenario to teach evidence collection, permission boundaries, approval, and positive verification without exposing production detail.

Review monitor recommendations before implementing them. A threshold copied from one incident can create false alarms or miss a different workload. Monitoring configuration and alert delivery remain the responsibility of the monitoring system; Usable preserves why the monitor exists and how its effectiveness was validated.

The technical investigation is private by default, but approved conclusions can inform other workflows without making raw operational data universally visible.

Public or customer-facing updates must distinguish observed fact, confirmed cause, expectation, and unresolved uncertainty. Do not publish raw traces, internal topology, credentials, customer identifiers, uncorroborated metrics, or a private operational theory. If a claim cannot be supported by the investigation, telemetry export, change record, agreement, or explicit approval, narrow it or leave it out.

Promote knowledge by audience, not by copying everything

Compounding happens through reviewed promotion:

  1. Observe privately. The incident team works from live telemetry and restricted operational evidence.
  2. Verify. The operator confirms cause, remediation, recovery, and residual risk.
  3. Structure. The working log becomes a linked Outage Investigation and Solution.
  4. Sanitise. Owners create audience-appropriate conclusions for service desk, customer delivery, onboarding, development, and communication.
  5. Connect. Approved fragments can be collected or linked across workspaces where permissions allow, while the restricted source remains restricted.
  6. Retrieve and challenge. A later incident starts with prior knowledge, then tests it against current evidence.
  7. Improve again. Differences, failed assumptions, and new verification update the solution, runbook, monitor, or standard after review.

That loop reduces repeated discovery without creating a dangerous global incident archive. A customer-facing colleague may see the approved impact summary, a developer the new test pattern, and an operator the full evidence chain. Each receives what the work requires, not everything the organisation knows.

Review the fragments before cleaning up the working log

The documentation workflow requires operator review of both linked fragments. Confirm that the root cause matches the evidence, the solution is actionable but bounded, verification is clear, monitor recommendations are implementable, residual risks are visible, links work both ways, and tags support retrieval.

Only after approval should the temporary investigation file be deleted or archived—and only with explicit operator permission. Keeping, archiving, or removing the working log depends on operational policy, legal retention, incident tooling, and whether the complete evidence already exists in the authoritative systems. Creating a Usable fragment does not override those retention obligations.

Corrections follow the same governance: update the affected fragment, re-review it, and preserve enough history to explain the change. A polished report that silently replaces inconvenient evidence weakens the memory it was meant to improve.

Where an investigation agent helps—and where it stops

With approved access, an AI agent can search Usable for runbooks and similar cases, fetch every full fragment it relies on, organise the working log, query separate telemetry tools, compare evidence, keep dead ends visible, draft hypotheses, prepare a remediation proposal, and create or update the reviewed fragments when given write permission.

Usable itself does not collect infrastructure telemetry, maintain incident status, run a service desk, deploy code, change production, send public statements, or prove recovery. Those capabilities belong to connected systems and accountable people. The investigation skill and documentation workflow are governed procedures stored in and used with Usable; they are not automatic product features that activate merely because a workspace exists.

An agent must stop for missing context, insufficient access, destructive or high-impact changes, approval, ambiguous customer obligations, and publication decisions. Engineers still supervise privileged and uncertain work. Agent-led investigation can reduce manual evidence gathering; it does not eliminate operational engineering, monitoring maintenance, or human judgement.

Current Usable capabilities and illustrative integrations

Current Usable capabilities

Usable provides workspaces and permissions, memory fragments with metadata and status, custom fragment types, collections, files and attachments, semantic and agentic search, full-fragment retrieval, dashboard access, REST, MCP, webhooks, and cross-workspace fragment links where permitted. In our operations workspace, custom fragment types and stored skills support the incident process described here. Other organisations design their own types, ownership, and review rules.

Illustrative workflow and integrations

Telemetry queries, alert routing, incident tickets, service targets, cluster inspection, change approval, remediation, deployment, soak monitoring, customer records, HR training, and public publishing require separately configured systems and credentials. Webhooks, REST, or MCP can connect parts of the flow, but Usable does not become the system of record for those operations. Any automatic routing, action creation, cross-workspace promotion, or communication approval described here is an implementation pattern that must be designed, permissioned, tested, monitored, and owned.
